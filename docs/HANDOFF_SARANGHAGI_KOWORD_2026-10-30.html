2. 사랑하기 때문에 — 무엇이 문제였고 어떻게 찾았나

사용자 지적: 「앞이 잘린다. 뒤는 늘어져도 되지만 앞이 잘리면 답답하다.」

2-1. 지우고 간 가설

  • 가드(앞 대사 꼬리 방지)가 시작을 민다 → ✗ 아님. 33줄 중 한 줄도 밀지 않음(측정). align.py 가 겹침을 풀 때 prev.e = next.s − 0.05 로 clamp 하므로 가드 조건이 성립하지 않는다.
  • 진짜 원인은 시작 시각 자체 + 리드인 기본값이 0 이라 여유가 아예 없던 것.

2-2. 통한 방법 ① — 후렴 반복 대조 (음원 불필요, 이 세션의 성과)

이 곡은 후렴이 정확히 288박 = 132.915초 뒤에 그대로 반복된다.

같은 가사 줄 두 개의 시각을 빼면, 보컬을 검출하지 않고도 어느 쪽이 늦은지 증명된다.

T = json.load(open('src/beats.json'))['beat_interval']   # 0.46151
DELTA = 288 * T                                           # 132.915
# 같은 가사 짝 (후렴1 id, 후렴2 id)
for a, b in pairs:
    off = (by[b]['s'] - by[a]['s']) - DELTA               # 0 이면 일치
  • 결과: 10쌍 중 8쌍이 어긋남, 최대 1.29초(#16 헤어지지 않으리).
  • 2쌍이 0.09초 이내로 맞아 Δ 자체가 옳다는 보증이 된다.
  • 늦은 쪽을 이른 쪽에 맞춤 → 8/10 → 0/10 (최대 0.005초).
다른 곡에도 쓸 수 있다. 조건은 같은 가사가 정확한 박자 간격으로 반복될 것 하나뿐이다.

2-3. 통한 방법 ② — 글자당 시간

tools/fix_cue_ends.py 가 쓰는 잣대와 같다(그쪽은 끝, 여기서는 시작).

  • 2번 「혼자만의 오해였던가요」는 10글자를 2.8초에 담고 있었다. 곡 중앙값 0.73초/글자면 7.3초가 필요하다.
  • 음원에서도 28.2~28.7 무음 뒤 28.8 → 35.2 가 6.4초 연속, 그리고 28.80 은 정확히 62번째 박.
  • 세 근거가 한 점을 가리켜 시작을 32.76 → 28.85 로 당김. 2.8초 → 6.7초.
  • 지금은 글자당 길이가 비정상인 줄 0장.

2-4. 실패한 방법 (다시 시도하지 말 것 — 보컬 분리 없이는 안 된다)

방법왜 실패했나
보컬 대역(250~3000Hz) 세기반주가 같은 대역을 채운다. 65~85초가 통째로 「소리 있음」
포먼트 비율(800~2800 / 80~400Hz)전주(반주만) 0.345 > 노래 중 0.240 — 역전된다
온셋 검출 + 역추적130BPM 이라 박마다 반주 온셋이 있어 보컬 온셋과 구분 불가
pe(발성 끝) 추정후렴 반복으로 검산하니 10쌍 중 7쌍이 최대 2.7초 어긋남 → 추측값이라 넣지 않았다

  2. koword-cards 를 반드시 다시 빌드한다. 그 앱의 예문 39개가 사랑하기 카드 번호(#saranghagi/c<id>)를 가리킨다. 번호가 밀린 채 두면 딴 줄로 간다.
  3. study.txt 는 번호가 아니라 본문으로 붙으므로 번호 재정렬 때 손대지 않아도 된다. 반면 ja.txt·rd.txt·fixes.txt·subtitles.srt 는 전부 id 키라 같이 재정렬해야 한다.

  5. 리드인은 optLead(기본 −0.3). 가드(optGuard)는 켜져 있어도 이 곡에서는 거의 작동하지 않는다(§2-1).
  6. 현재 브랜치는 feat/courage-lyrics 이고 이 세션 이후 다른 작업이 많이 쌓였다. git log 로 최신 상태를 먼저 확인할 것.
  7. ⚠️ 이 세션은 main 에 직접 푸시했다. 사용자가 매번 「배포해봐」라고 지시했기 때문인데, 이 리포의 규칙은 브랜치 → PR, 머지는 사용자 다(docs/HANDOFF_2026-10-30.md 참조). 이어받는 세션은 이 패턴을 따라 하지 말고 브랜치에서 작업할 것.
